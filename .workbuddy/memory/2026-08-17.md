# 2026-08-17

## GM6020 例程排障：串口 "Start!" 重复输出 4~5 次

排查结论（仅分析，未改代码）：

- `printf("Start!\n")` 在 `Core/Src/main.c` 的 `Sys_Init()` 中，且 `main()` 只调用一次 → 重复打印 = 芯片反复复位。
- 代码中无 IWDG/WWDG/软件复位（`NVIC_SystemReset`）；CSS 触发走 NMI → `while(1)` 死循环；HardFault → `while(1)` 死循环。故复位只能来自硬件：上电/BOR 或 NRST。
- 最可能根因：上电瞬间 VDD 跌落触发 Brown-Out Reset（GM6020 电机 + CAN 收发器启动电流拉低电压），复位几次后电源稳定，与"重复四五次后正常"吻合。

顺带发现的代码 bug（供后续修复参考）：
1. `Sys_Init()` 中 `CAN_FilterTypeDef FilterConfig;` 未清零，`FilterIdLow`/`FilterMaskIdLow` 为垃圾值。
2. `GM6020_Init()` 调 `GM6020_Reinit(pGM6020->ID)`，但 `ID` 字段从未赋值（恒 0），`Reinit` 直接 return，电机结构体实际未初始化。
3. `for (ID=1; ID<GM6020_ID_MAX; ID++)` 少初始化 ID=7（off-by-one）。
4. `GM6020_SendCurrentConfig()` 每 10ms 调一次 `HAL_CAN_Start()`（多余）。
5. `configTOTAL_HEAP_SIZE=4096` 偏小（3 任务×256 字 ≈ 3.5KB，余量小）。

## 追加线索（用户反馈）

- 用户反馈：加 `HAL_Delay` 无效；**单步调试则正常**。
- 这坐实了"全速运行才复现、与时间/负载相关"，而非代码逻辑 bug。指向两类：供电跌落 BOR（全速电流大→VDD 跌→复位）或 CSS+HSE（晶振临界→NMI 卡死）。
- 一锤定音手段：读 `RCC->CSR` 复位标志（PINRSTF/PORRSTF/IWDGRSTF/SFTRSTF）判断复位源；或示波器抓 NRST/VDD。

## 追加线索 2（用户反馈：软复位也一样）

- 用户反馈"调试软复位也是一样的"→ 排除"上电瞬间瞬态"，复位是**全速运行才复现**的，任何复位源（上电/软复位）后都会再触发。
- 结论方向不变：全速电流大→VDD 跌→BOR，或 NRST 被外部（USB-TTL 的 DTR/RTS 自动复位电路）拉低。读 `RCC->CSR`：PORRSTF=电源/BOR，PINRSTF=NRST 引脚。

## 新发现的代码 bug（确定存在，但发生在调度器之后，非 "Start!" 直接原因）

6. **PID 函数签名不一致**：`PID.h` 声明 `double PID_Caculate(PID_HandleTypeDef*, double, double)`，而 `PID.c` 实现为 `float PID_Caculate(PID_HandleTypeDef*, float, float)`。PID.c 未 include PID.h、自己重定义了结构体，故编译器不报错；调用方按 double 传参（寄存器对），被调方按 float 读 → PID 输入全乱、输出垃圾。
7. `PID_Init()` 声明了但从未被调用 → PID 增益(Kp/Ki/Kd 等)恒为 0（全局 bss 清零），PID 输出恒 0，电机实际不会被驱动。
